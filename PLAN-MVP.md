# Khazar Bridge — план MVP маркетплейса (Kaspi-лицо, B2B-начинка)

Дата: 15.09.2026. Решения зафиксированы с юзером:
- **Модель:** B2B-опт с витриной в стиле Kaspi/WB (партии, MOQ, Incoterms, RFQ → котировка → контракт → отгрузка).
- **Кодовая база:** форк **Odezhda** (Next.js 16 + Turso + Drizzle + NextAuth + Tailwind) + **EDO** как сервис договоров по API.
- **Деньги:** платформа расчёты не проводит. Доход = подписка продавца + комиссия за подтверждённый контракт.
- **Договор:** ЭЦП НУЦ РК для казахстанской стороны + простая подпись (OTP) для иранской, hash-chain как доказательство, PDF RU/EN/FA с QR-верификацией.
- **Уведомления:** только **внутри платформы** (лента + колокольчик, хранение в БД). Никаких внешних каналов в обязательном контуре — WhatsApp/Telegram в Иране заблокированы, Web Push и FCM идут через Google и из Ирана нестабильны. Внешние каналы — опциональная надстройка для казахстанских пользователей.

## 2а. Модуль внутренних уведомлений (решение 15.09)

Всё, что платформа сообщает сторонам, живёт в её собственной БД и показывается в интерфейсе. Пользователь, который не заходил неделю, при входе видит всю историю — ничего не теряется на блокировках мессенджеров.

### Таблицы
| Таблица | Назначение |
|---|---|
| `notifications` | `id`, `recipient_type` (user/seller), `recipient_id`, `type`, `entity_type`, `entity_id`, `payload` (JSON), `priority`, `read_at`, `created_at` |
| `notification_prefs` | какие типы событий показывать/скрывать, по получателю |
| `notification_reads` | отметки прочтения для событий, адресованных всей компании-продавцу (несколько сотрудников на одного `seller`) |

**Ключевое правило: текст уведомления в БД не хранится.** Храним `type` + `payload` (числа, id, суммы), а формулировку рендерим на языке получателя — RU / EN / **FA**. Иначе иранский продавец получит русскую строку. То же касается дат, валют и направления письма (RTL).

### Доставка в браузер
- **SSE** `/api/notifications/stream` — с нашего же домена в КЗ, без сторонних сервисов (Pusher, Firebase, OneSignal из Ирана недоступны либо нестабильны);
- **fallback polling** раз в 30 с — иранские каналы рвут долгоживущие соединения, SSE обязан переподключаться, а при неудаче молча уходить в polling;
- счётчик непрочитанных отдаётся одним лёгким запросом, лента — постранично.

### UI
Колокольчик со счётчиком в шапке → выпадающая лента последних → страница «Уведомления» с фильтрами по типу и сделке. Каждое уведомление ведёт на сущность: RFQ, котировку, сделку, договор, отгрузку.

### События B2B
Новый RFQ продавцу · поступила котировка покупателю · котировка принята/отклонена · смена стадии сделки (Новая → Котировка → Контракт → Отгрузка) · договор сформирован и ждёт подписи · подписан второй стороной · отгрузка в пути / прибыла · товар прошёл модерацию · истекает подписка продавца · счёт на комиссию.

### ⚠️ Исключение: код подписи договора
OTP для простой электронной подписи **нельзя** доставлять этой же лентой: пользователь в ней уже авторизован, и такой «код» не является вторым фактором — доказательная сила подписи падает. Код подписания уходит на **email или SMS** (email устойчивее всего в Иране), а лента показывает только «договор ждёт вашей подписи». Все остальные уведомления — внутренние.

## 3. Архитектура

```
khazarbridge.kz  (VPS/Plesk в Казахстане — обязательно, Vercel/GitHub блокируют Иран по OFAC)
│
├── storefront (Next.js)      витрина Kaspi/WB: каталог, фасеты, карточка, «запросить партию»
├── cabinet   (Next.js)       кабинет продавца и покупателя, сделки, документы  ← форк Odezhda
├── core API                  каталог, склад, сделки, фрахт, тарифы            ← Odezhda API
├── contracts API  ──HTTP──▶  EDO (шаблоны, согласование, ЭЦП, PDF+QR, аудит)
└── notifications             своя БД + SSE/polling с домена в КЗ (колокольчик, лента)
                             email/SMS — только для кода подписи договора
```

**Хостинг: VPS hoster.kz** (решение юзера 15.09). Почему именно в КЗ — проверено на текущем демо: Vercel и GitHub Pages не отдают контент посетителям из Ирана.

**Рекомендуемая конфигурация:** 2 vCPU / 4 ГБ RAM / 50+ ГБ SSD, Ubuntu 22.04 или 24.04. Четырёх гигабайт хватает на сборку Next.js (со swap, который ставит скрипт) плюс работу приложения; на 2 ГБ сборка упирается в память — это мы уже проходили на Oracle micro.

**Готовые файлы выкатки** (`deploy/platform/`, написаны 15.09 — прежние `deploy/deploy.sh` и `nginx-khazarbridge.conf` рассчитаны на статику и для платформы не годятся):
| Файл | Назначение |
|---|---|
| `setup-server.sh` | первичная настройка: Node 22, nginx, certbot, ufw, fail2ban, swap 2 ГБ, пользователь `khazar`, структура `/srv/khazarbridge/{releases,shared,current}` |
| `nginx-platform.conf` | reverse proxy на :3000; **для `/api/notifications/stream` отключены `proxy_buffering` и кеш** — иначе nginx копит SSE-поток и лента уведомлений не доходит до браузера |
| `khazarbridge.service` | systemd: автозапуск, `Restart=always`, `MemoryMax=2G`, env из `shared/.env` |
| `deploy-app.sh` | выкатка релизами с симлинком `current`, сборка на сервере, миграции, рестарт, проверка что сервис поднялся, хранение 5 последних релизов |
| `backup.sh` | `sqlite3 .backup` + архив загрузок, ротация 14 дней, **обязательная копия на внешний хост** |

**База данных.** Odezhda работает на Turso (libSQL) через Drizzle. На своём VPS берём **локальный SQLite-файл** — Drizzle с драйвером libsql принимает `file:` URL, так что код и схема не меняются вообще, а база лежит в `shared/db/` и переживает выкатки. Для B2B-нагрузки (сотни продавцов, тысячи RFQ) этого с запасом хватает; ограничение SQLite — один писатель одновременно, и когда упрёмся, переезжаем на PostgreSQL отдельным шагом. Плюс локальной базы: никакой зависимости от внешнего облака и латентности до Индии, где сейчас живёт Turso-инстанс Odezhda.

**Бэкапы — с первого дня.** Урок 185.98: провайдер переустановил сервер, и свежего дампа не оказалось, самый новый был шестимесячной давности. Поэтому `backup.sh` ставится в cron сразу при поднятии, и копия обязана уезжать за пределы VPS — например на наш Oracle-сервер или на Mac (адрес задаётся в cron, в репозитории не хранится).

**⚠️ Cloudflare перед сайтом не ставим.** Для `truest.kz` мы привыкли к CF, но Cloudflare ограничивает обслуживание Ирана, и оранжевое облако рискует отрезать ровно ту аудиторию, ради которой мы уходим с Vercel. DNS держим в режиме DNS-only, A-записи смотрят прямо на IP hoster.kz.

## 4. Этапы

**Этап 0 — подготовка (1–2 дня)**
Купить `khazarbridge.kz` и `.com`; поднять VPS на hoster.kz (2 vCPU / 4 ГБ, Ubuntu 22.04+), дать SSH-ключ; прогнать `deploy/platform/setup-server.sh`; направить A-записи на IP (DNS-only, без прокси CF); форкнуть Odezhda в новый репо `khazarbridge-platform`, ветка `codex/test`; поставить `backup.sh` в cron с копией наружу.

**Этап 1 — каталог и витрина (неделя 1)**
Перенос 46 позиций из `data.js` в БД; сущность `sellers` и привязка товара к продавцу; витрина в стиле Kaspi (фасеты: направление, категория, цена, MOQ, Incoterms, срок); карточка с калькулятором партии и фрахтом; RU/EN/FA + RTL.

**Этап 2 — сделка (неделя 2)**
RFQ → котировки → выбор → сделка; кабинет продавца (свои товары, входящие RFQ, котировки); уведомления в WhatsApp/Telegram; стадии как в демо (Новая → Котировка → Контракт → Отгрузка).

**Этап 3 — договор (неделя 3)**
Двуязычные шаблоны: контракт поставки, спецификация, инвойс, packing list. Интеграция с EDO: создание документа, маршрут согласования, ЭЦП НУЦ РК для КЗ-стороны, OTP-подпись для иранской, PDF с QR, публичная верификация, вебхук статуса обратно в сделку.

**Этап 4 — деньги платформы и запуск (неделя 4)**
Тарифы продавцов и комиссия за подтверждённый контракт; модерация и KYC; сид реальных поставщиков; деплой на `khazarbridge.kz`; проверка доступности из Ирана.
